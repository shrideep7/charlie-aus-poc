What they actually asked for

The brief is unusually precise, and it is not a request for software capability. It is a test of a service proposition: when the desk is unattended at 7pm, can one agent hold the entire tenant relationship without the tenant learning three different systems?

One line of the brief carries the whole specification — Charli should “understand natural-language requests, provide immediate assistance, coordinate simple related tasks, make simulated bookings/requests and connect tenants to the appropriate support pathway.” Five verbs. Every part of the demo exists to make one of them visible.

VerbHow the demo proves it
Understands natural languageFree-text input, no menu required; four intents parsed from one sentence
Provides immediate assistanceBuilding knowledge answered from the cached prompt — no round trip, no waiting
Coordinates related tasksThe hero journey: room, guest passes, breakfast and an airport taxi from one request
Makes simulated bookingsFour reference families — BK CH CS VA
Connects to the right pathwayFive simulated teams, four escalation tiers, correct routing every time

The brief also grants an explicit licence — “not to replicate current operating procedures or build a production-ready solution” — and rules out every integration, authentication, live data and analytics. We should take that licence in full. The bar is believability and clarity of the service model, not correctness. No database, no login, no external systems.

Three surfaces, one configuration

The brief asks for a standalone experience “configured for 1 Martin Place”. That phrase is load-bearing: the asset, service menu, room catalogue, teams and recommendations are configuration, not code — and a presenter screen exists purely to show that configuration.

Tenant Charli chat

Mobile-first conversation with rich cards for room options, confirmations, guidance and the closing itinerary. Warm, concise, never a technical caveat.

Presenter only Trace panel

Per turn: intents, extracted entities, confidence, rules applied, actions, outcome — plus urgency, destination team and hand-off summary on escalations.

Presenter only · static Configuration view

Asset, operating model, enabled services, room catalogue and rules, escalation teams, recommendation set. Rendered from the live config objects. No editor.

Because all three read the same five data modules, the closing line of the demo is true rather than aspirational: a second building is a new configuration file, not a new build.

How it is built

One Next.js application in TypeScript. Three routes, static data, and a streaming agent endpoint running Claude Opus 5 with six tools. Deployed to a single URL, with a local build held in reserve.

Two decisions that protect the demo

Safety copy is deterministic, never generated. The brief quotes four escalation scripts word for word, including an emergency script that instructs the tenant to call 000. A model asked to “say this” will paraphrase it roughly one time in ten. Paraphrasing an emergency instruction, on stage, in front of a client holding the exact wording, is the worst failure available to us. The model chooses the tier; the copy is substituted in code.

Please call 000 now and move to a safe area if you can. I’m alerting Building Support and recording your location as [location]. Emergency tier — emitted byte-identical, asserted by test

Reference numbers are pre-seeded to match the client’s document. The brief’s own worked examples use BK-MP-1042, VA-MP-1051, CS-MP-4108 and CH-MP-3018. The allocator serves exactly those first. When the hero journey runs, the numbers on screen match the numbers in their pack — a thirty-minute build, and the detail that tells the room we read all 184 lines.

The hero journey

One utterance, four intents. The brief allows seven conversational turns; we land it in five by pairing each question with the previous step’s result.

I have six interstate clients arriving at 8am tomorrow. Please arrange a room, organise guest passes, recommend breakfast nearby, and book a taxi to the airport for one guest after the meeting. Opening request
Turn 1 Names all four parts back; asks duration only Multi-intent recognition, and asking for nothing it already knows.
Turn 2 Recommends Park Meeting Room 08:00–09:30, alternative The Forum Quiet Room fails on capacity, Pitt opens at 09:00, Martin Boardroom is blocked until 10:00 — only Park works. The approval rule on The Forum is surfaced, not hidden.
Turn 3 Books it; asks for guest names and companies BK-MP-1042
Turn 4 Passes ready; two breakfast options; proposes a 09:45 pickup and asks only for the terminal The 09:45 is inferred from the 09:30 finish rather than asked for. This is the moment the room leans forward — rehearse it. VA-MP-1051
Turn 5 Taxi arranged; one concise itinerary carrying every reference CS-MP-4108

Four cheap insurances

  • Golden transcript harness — replays every prompt in the client’s pack and asserts routes, reference formats, verbatim safety copy, turn counts and the absence of hedging language. Runs the morning of the demo.
  • Rails mode — deterministic canned playback of the hero journey and the top eight prompts, no API calls. If the venue network drops mid-demo, the presenter switches and nobody in the room knows.
  • Presenter reset — clears the session and re-seeds references, so the hero journey runs cleanly twice. It will need to.
  • Recorded backup — four minutes of hero journey and one escalation, on the laptop. Twenty minutes to make.

Deliberately not building

The brief excludes these, and the last guardrail forbids adding anything that does not replace something already in scope. Agreeing the list in advance means an in-room request becomes a production-phase conversation rather than a scope change four days before the demo.

  • Login or SSO
  • Tenant profiles
  • Any live integration
  • Interactive map or wayfinding
  • Payments
  • Analytics dashboard
  • Admin or config editor
  • Voice input
  • Mobile app
  • Multi-building switcher
  • Notifications or email
  • A second hero journey
